# Claude 透传流空闲超时：统计依据与本地修复

记录日期采用任务本地日期 2026-09-15（Europe/Amsterdam）；下列生产统计窗口和日志时间均为北京时间（UTC+8）。

## 范围与结论

- 用户授权根据近期生产数据选择等待阈值，修改并提交超时相关代码；本次没有推送、部署、重启、修改生产配置或执行真实上游推理请求。
- 只读核验服务器 1 当前镜像为 `saviour2411/sub2api:0.1.234`，生产使用 Anthropic API Key 透传路径。
- 建议保留普通流空闲阈值 **180 秒**，先修复周期检查导致的额外等待；示例值由 300 秒统一为 180 秒，后端默认数值不变。
- 本次只修正 Anthropic API Key 透传的计时精度，不修改其他转发路径、首 Token 分组策略、重试、失败停调度、计费或资源配置。

### 为什么不直接改成 60 或 90 秒

现有用量表没有最大相邻事件间隔、最后语义输出时间或终止事件状态。透传路径的 `first_token_ms` 取第一条非空 SSE data 到达时间，可能仅是 `message_start`；它不等于首个答案或思考输出时间。

所以总耗时较短只能说明多数请求较快，不能据此证明把空闲阈值降低到 60/90/120 秒不会中断正常长思考。`output_tokens=0` 也不能证明未输出内容，最终用量可能因流中断而缺失。本次选择保留既有 180 秒容忍，先消除已确认的计时偏差。

## 本地修改及边界

1. 透传路径把周期计时器改为单次计时器。检查时如果刚收到数据，只按“阈值减去已空闲时间”重新计时，而不再等一个完整阈值。
2. 保留每一条上游读取行更新活跃时间的语义，包括心跳、注释和空行；下游自行发送的保活仍不能延长上游空闲期限。没有顺带改成“语义停顿超时”。
3. 完整 `message_stop` 仍立即结束，缺失终止事件仍报错，客户端断开后继续排空并保留已观测用量；`0` 仍表示禁用空闲超时。
4. `deploy/config.example.yaml` 的普通流示例值由 300 改成 180，添加与后端默认值一致性回归；图片流 900 秒等其他数值不变。
5. 没有改变生产持久化配置。只有后续明确授权部署新镜像后，生产透传路径才会使用本次精准计时逻辑。

此修复不限制请求总时长：间隔小于阈值的持续长流仍可运行超过三分钟。但以前依赖检查偏差额外存活的 180～360 秒空闲流会更早结束；历史数据不足以证明零误伤，部署后仍需观察。持续上游心跳但没有有效输出的长等待、首输出前重试和备用渠道不在本次范围内。
