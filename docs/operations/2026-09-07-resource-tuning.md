# 服务器1资源升级后的实例参数调整

关联能力：`CUST-OPS-005`。应用版本保持 `0.1.229`。

## 范围与原因

服务器升级至 12 vCPU、约 32 GiB 内存后，实例仍保留四核时期的 Go 和数据库缓存配置。本次仅调整以下四项，释放新增资源可用空间，不改变业务限额和仓库通用默认值。

| 配置 | 调整前 | 调整后 | 实际生效验证 |
| --- | --- | --- | --- |
| `GOMAXPROCS` | `4` | `12` | 应用容器环境为 `12` |
| `GOMEMLIMIT` | `3GiB` | `10GiB` | 应用容器环境为 `10GiB` |
| `POSTGRES_SHARED_BUFFERS` | `512MB` | `4GB` | `SHOW shared_buffers` 返回 `4GB` |
| `POSTGRES_EFFECTIVE_CACHE_SIZE` | `4GB` | `16GB` | `SHOW effective_cache_size` 返回 `16GB` |

`GOMEMLIMIT` 是 Go 运行时软内存限制，不是容器硬上限；`effective_cache_size` 是查询规划器的缓存估值，不会直接分配对应内存。

## 实施与安全边界

- 时间采用服务器北京时间：2026-09-07 02:55:01 开始变更，02:55:52 完成重建与健康确认，合计约 50 秒；该时长包含 Docker 健康检查等待，不等同于逐秒测量的不可用时长。
- 原 `.env`、双生产 Compose、持久化应用配置仅备份到工作区内受限权限、被 Git 忽略的目录，未提交凭据或实例连接信息。
- 写入前确认候选 `.env` 仅有四项字节差异，Compose 解析也仅有这四项差异；核验旧实例健康、精确 bind mount、镜像指纹及双 Compose 一致性。
- 先停止应用并等待清理，再重建 PostgreSQL，数据库健康后重建应用。使用活动 `docker-compose.yml`，限定目标服务并禁止构建、拉取镜像，没有执行 `down` 或清理数据/卷。
- 这是单实例维护，执行前仍有长请求，不能视为无损滚动升级。Docker 的 60 秒停止等待不会把应用内部 5 秒优雅退出期限延长至 60 秒；本次未逐请求核实中断数量。
- PostgreSQL 实际数据目录、三项生产 bind mount、仅回环暴露、HTTP upstream 业务开关及应用镜像指纹不变。Redis 容器标识和启动时间不变。
- 数据库连接池保持 `80/32`，PostgreSQL 最大连接保持 `100`；用量 worker 保持 `64`、队列 `16384`、超时 `5` 秒、关闭自动扩容，按用户串行扣费不变。其他数据库、HTTP、Redis 性能参数不变。
- 两份生产 Compose 未修改且字节一致；持久化应用配置未修改，保留 `gateway.response_header_timeout: 3600`，OpenAI/Codex、Grok 独立超时不变。

## 回滚

需要回滚时，仅恢复表格中的四项旧值；若期间存在其他配置变更，不得用整份历史 `.env` 覆盖。回滚前重新执行生产挂载、双 Compose、镜像和健康核验，并评估正在处理的长请求。
