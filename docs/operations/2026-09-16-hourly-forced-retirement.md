# 一小时排空与超时强制退役

日期：2026-09-16，时间均为北京时间。关联 `CUST-OPS-001`、`CUST-OPS-003`。本记录替代此前“超时无限保留、不强制停止”的生产发布策略，不改写历史验收结果。

## 用户授权后的新策略

- tag Release 使用 `--window 3600 --force-after-window`；生产部署 job 上限从60分钟改为120分钟，容纳候选准备、一小时观察及回收。
- 从实际切流／回滚切流时间累计一小时，中断重跑不重置观察起点。旧状态缺少新字段时使用已记录的切流时间；缺少时间或身份信息则拒绝猜测。
- 一小时内，只要生命周期为 `drained`、旧 Nginx worker 已退出，就使用原有退役凭据路径正常关停、回收，不必等满一小时。
- 到期仍未排空，先确认活动实例身份、应用端口及 API/direct 两入口就绪，再对固定旧容器ID执行 `docker stop -t 60`：SIGTERM后最多给60秒收尾，仍未退出由Docker强制停止。不是要求“一小时整完成所有清理”；其后还有关停和路由清理时间。
- 强制路径可能中断旧 SSE/WS/HTTP、使旧会话无法继续，并可能漏收上游最终用量。不修改正常请求超时，不伪造终止事件、不重试生成请求、不重算历史账单；不能再宣称超时请求无损。
- 不增加应用强制管理接口，现有已部署镜像也能使用该执行器。原SIGTERM处理会等待租约，超时路径可能最终需要SIGKILL，须据退出码如实记录。

## 安全与恢复

1. 与生产发布共用 `deploy.lock`；强制目标必须是 `pending` 且不同于 `active`。旧容器的生产数据挂载必须匹配。
2. 保存旧实例／容器、活动实例／容器、执行发布提交、强制原因及关停前工作快照；恢复逐项匹配，不以槽名代替进程身份。旧管理接口失联时仍等待原期限，到期且活动实例就绪才强制停止固定旧容器；快照标为未知，不假设工作为0。
3. 在 `force_retiring` 状态持久化关停起点，重跑不重置60秒关停预算，不重建活动实例。
4. 停止后先记录退出码、OOM、日志取证、可见用量丢弃数，再删容器。退出137或日志缺失不得报告 `clean_exit=true`；`usage_loss_unknown=true` 表示不能证明未漏用量。
5. Redis按批次SCAN，以当前值等于旧实例ID为条件删除 `lifecycle:affinity:*`。只删除该实例的 `lifecycle:live:<id>`；保留 `lifecycle:known:<id>` 供其他并发状态确认死亡，不清库、不删其他实例归属或历史用量。
6. 批量COUNT=1000；超过60秒保存游标和已删除计数，保留中间状态供重跑。COUNT为扫描提示值，不是固定返回数量。
7. 确认旧容器停止、旧代理退出，清理旧socket后才移除旧槽记录、恢复 `stable`。下一tag可复用固定端口。
8. 不强杀整组Nginx worker，以免影响同机其他站点。旧代理仍在时，即使旧应用已停止也保留 `force_retiring`、禁止复用槽位，待代理退出再恢复；避免旧代理将流量送入同端口新实例。
9. `forced_retire_result` 与自然退役凭据分开保存，不伪造 `drained` 凭据或用 `drained_at` 声称自然排空；Release摘要展示强制结果和中断风险。

直接运行脚本但不传 `--force-after-window`，超时仍保留旧实例；tag工作流明确启用强制策略。一次性v0.1.234 legacy门禁保持原语义，不把未知旧版套用新强制路径。

## 只处理待退役槽

在server1用已审核的新执行器运行：

```bash
python3 /path/to/reviewed/deploy.py \
  --directory /root/proj/sub2api/deploy \
  --retire-pending --window 3600 --force-after-window
```

不启动候选、不切流、不打tag，但期限已过时会立即开始强制关停；这不是只读命令。不要用不可恢复的手工 `docker rm -f` 替代。

脚本／Actions意外停止时仍需恢复已保存操作。本变更延长观察并执行超时分支，没有新增长期驻留的后台执行器。
